# Releasing zioshade

zioshade follows [SemVer](https://semver.org/) on the public API exported from `src/root.zig` and on
the C ABI declared in `include/zioshade.h`. A release is a tag; there is no publishing step beyond
pushing it, because consumers fetch the repo archive directly from `build.zig.zon`.

Tagging is a maintainer action. Everything below except the tag itself goes through a normal PR.

## Sequence

1. **Refresh the generated numbers.** See "Numbers that go stale" below. Do this first, because it
   can change what the release notes have to say.

2. **Bump the version.** Set `.version` in `build.zig.zon` to the new `X.Y.Z`. That field is the only
   place the version lives.

3. **Close the CHANGELOG section.** In `CHANGELOG.md`, rename `## [Unreleased]` to
   `## [X.Y.Z] - YYYY-MM-DD` and open a fresh empty `## [Unreleased]` above it. Use the date of the
   most recent commit on `main`:

   ```bash
   git log -1 --format=%cs origin/main
   ```

   Then read `git log vPREV..origin/main --oneline` and check that every user-visible change is
   represented. Anything that changes generated output, the public Zig API, the C ABI, or an error
   the caller can observe belongs in the section. Additive C ABI changes (a new `zioshade_status_t`
   value, for example) must be called out explicitly, because a consumer switching exhaustively over
   the enum needs a default branch.

4. **Verify locally.**

   ```bash
   mise exec -- zig fmt --check src
   just ci
   ```

   `just ci` mirrors the CI workflow's job set on one OS and one toolchain: necessary, not
   sufficient. `just ci-full` adds the gates hosted runners cannot run (DXC, Metal, the spirv-cross
   and naga differentials); run it before a release.

   Also build on Zig 0.16, which CI covers and `just ci` does not:

   ```bash
   /opt/homebrew/bin/zig build   # or whatever 0.16 toolchain is on the machine
   ```

5. **Merge the release PR and wait for CI.** Every job on `main` must be green before tagging:
   `fmt`, `build-test`, `conformance` (which runs `strict-gate --min-pass=N`), `spv-validity`,
   `cts-ingestion`, `fuzz-smoke`, `c-abi`, `package-smoke`. A red job is a release blocker, not a
   flake to retry past.

6. **Tag and push the tag.**

   ```bash
   git checkout main && git pull
   git tag -a vX.Y.Z -m "vX.Y.Z"
   git push origin vX.Y.Z
   ```

   Tags are `vX.Y.Z`, matching `v0.3.0` and `v0.4.0`.

7. **Cut the GitHub release** against that tag, with the CHANGELOG section for `X.Y.Z` as the body.

## Numbers that go stale

Two sets of numbers in this repo are snapshots of a real run and have no gate keeping them honest.
Both have drifted before, so refresh them as part of the release and say so in the PR.

- **`docs/STATUS.md`** is generated by `just status` (`tools/gen_status.sh`), which runs
  `zig build conformance` and writes the counts along with the commit and a UTC timestamp. It is
  cited from `CONTRIBUTING.md` as the authoritative conformance count, so a stale copy misstates the
  project's own baseline. Re-run `just status` and commit the result. Requires `spirv-val` on
  `PATH`.

- **`BENCHMARKS.md`** carries a hand-committed table from `zig build bench-compare`, labelled with
  the machine, OS, Zig version and Vulkan SDK it came from. Re-run it and update both the table and
  that label, or, if the release is not being cut on a comparable machine, leave the numbers alone
  and make the existing "as of" label say which commit they were measured at. Do not carry a number
  forward because it still looks plausible.

`docs/` also holds several hand-written status and analysis documents
(`IMPLEMENTATION_STATUS.md`, `COVERAGE_MATRIX.md`, `DIFFERENTIAL_PROOF.md`, `RENDERING_RESULTS.md`).
Skim them for claims the release invalidates.

## What not to do

- Do not tag from a branch, or before CI on `main` is green.
- Do not hand-edit `docs/STATUS.md`; it says so at the top of the file.
- Do not move or delete a published tag. Consumers pin archive URLs by tag, so a moved tag changes
  the hash under them. Ship a new patch version instead.
